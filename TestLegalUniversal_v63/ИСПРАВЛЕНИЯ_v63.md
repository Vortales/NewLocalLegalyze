# ИСПРАВЛЕНИЯ_v63

Версия `2.19.0` (`universal-embedded-v63`, сборка `2.19.0.0`). Основа — папка
`TestLegalUniversal_v62`. Материал — выгрузка `Постановление.7z`: сессия
`20261125-214026-17492-1ad66b`, дело №1 в работе (`cases/1/case.json`),
готовые документы этапов 1 и 2, а также образцы постановлений этапа 1.

Образцы из выгрузки сохранены в `tests/samples_v63/` — на них построены тесты,
чтобы правки не «проверялись» придуманными строками:

| Файл | Что это |
|---|---|
| `ответ_этап1_с_цепочками.txt` | полный ответ ИИ на этап 1: решение «Принято» + три цепочки |
| `испорченный_установил_этап1.txt` | документ этапа 1, в котором «УСТАНОВИЛ» заполнен служебным текстом |
| `ответ_постановление_этап2.txt` | ответ с постановлением этапа 2 — образец правильного «УСТАНОВИЛ» |

## П.1 — кнопка «Этап 1» недоступна после вставки обращения

**Замечание:** «Вставил Обращение в „Обращение (вставить целиком)“ — пытаюсь
нажать на кнопку „Этап 1“, а она недоступна. Нажимаю на „Проверить ещё раз“,
чтобы прогнать в чате с ИИ».

**Причина.** Текст обращения записывался в дело только в обработчике сигнала
поля (`_on_appeal_changed`) — а доступность главной кнопки считал
`ogp_stages.node_state()` по `case.appeal_raw`. Пока сигнал не отработал (или
если дело было загружено иначе), кнопка оставалась выключенной: пользователь
вставил текст, увидел серую кнопку и пошёл в обходной путь через перепроверку.

**Исправлено:**

* текст обращения пишется в дело прямо в `_on_appeal_changed`, и сразу же
  пересчитывается главная кнопка (`_refresh_main_action()`);
* `node_state()` для узла «1» разрешает запуск всегда, когда текст обращения
  есть — повторный прогон этапа 1 тоже разрешён;
* подсказки у поля говорят «нажмите „Этап 1“» (раньше — «Проверка ИИ»,
  отдельной кнопки с таким названием нет с v62).

## П.2 — «УСТАНОВИЛ» содержал служебный текст

**Замечание:** «Проанализируй ИИ-документ.txt, в частности „УСТАНОВИЛ“».

В выгрузке раздел выглядел так (сокращённо):

```
УСТАНОВИЛ:
Проверь обращение. Текст обращения — во вложении «Обращение.txt», порядок
проверки и формат ответа — в файле заявки… ПРОВЕРКА ОБРАЩЕНИЯ Состояние:
Принято Что проверить: … КОНЕЦ ПРОВЕРКИ ЦЕПОЧКИ ЭТАПА 2 ЦЕПОЧКА A: … ЗАЧЕМ: …
```

То есть в бланк попали: наша собственная реплика из чата, пересказ служебного
блока проверки и обе цепочки этапа 2. Ни одна из этих строк не является
установленным фактом.

Как должно быть — по образцам из той же выгрузки (`этап-2 — санкция`,
`Постановление №1/LSCSD-IAD-1`): после «УСТАНОВИЛ:» идут только фактические
обстоятельства (что поступило, что установлено, правовая квалификация, вывод
по проверке), затем «ПОСТАНОВИЛ:» с пунктами.

**Что сделано** (`postanovlenie_prokuror_data.py`):

1. `strip_service_blocks()` вырезает блоки целиком по маркерам, в том числе без
   `===`: «ПРОВЕРКА ОБРАЩЕНИЯ … КОНЕЦ ПРОВЕРКИ», «ЦЕПОЧКИ ЭТАПА 2 … КОНЕЦ
   ЦЕПОЧЕК», «ПЛАН ЭТАПА 2 … КОНЕЦ ПЛАНА».
2. `strip_instruction_sentences()` убирает предложения-инструкции чата
   («Проверь обращение…», «Текст обращения — во вложении…», «Порядок проверки и
   формат ответа — в файле заявки…», «Ответь только служебным блоком…», «Вы
   отправили N файлов…»). Режется по предложениям, потому что ИИ склеивает их в
   один абзац с фактами.
3. `drop_service_lines()` убирает строки служебных полей («Состояние: …»,
   «Что проверить: …», «Вид решения: …», «Удостоверение нарушителя: …»).
4. `clean_established()` собирает это в один вход и дополнительно обрезает
   оборванный хвост (v54). Чистка применяется и ко всему тексту до разбора
   (`parse_gov_answer`), и к собранному разделу «УСТАНОВИЛ» — повторно
   безопасна (идемпотентна, проверено тестом).

Проверка на образце: было 3105 символов служебного текста → осталось пусто,
то есть весь раздел был мусором; на ответе этапа 2 «УСТАНОВИЛ» сохраняется
целиком (3142 символа фактов), ни одна служебная строка не появляется.

Промт не менялся: он и раньше запрещал такое (`8.1.1`, «ЗАПРЕТ ЛИШНЕГО
МАТЕРИАЛА В „УСТАНОВИЛ“»), но ИИ его не выполняет — поэтому чистка делается на
стороне клиента, как и остальные защиты v54–v62.

## П.3 — перезагрузка браузера и «Закрыть обращение»

**Как должно быть (со слов пользователя):**

1. создаю обращение → вставляю текст в «Обращение (вставить целиком)» →
   нажимаю «Этап 1»;
2. если «В процессе», то есть решение «принятие», — **автопереход** на вкладку
   «Цепочка этапов»; там в «Этап 1. Решение по обращению» стоит «принятие», а в
   «Этап 2. Цепочка постановлений по существу» — три варианта цепочки из того же
   ответа ИИ;
3. если «отказ» или «переадресация» — дальше ничего не выполняется;
4. «Сформировать» этапа 1: браузер обновляется, и уже после обновления уходит
   текст для формирования .png;
5. подэтапы этапа 2 и этап 3 — **без перезагрузки**: ИИ должен помнить этапы 1,
   2 и 3 и не переписывать вынесенное;
6. на этапе 3 — кнопка **«Закрыть обращение»**: дело отработано, браузер
   перезагружается.

**Что сделано:**

* `refresh_case()` после ответа этапа 1 сам открывает вкладку «Цепочка этапов»
  (`_goto_chain_after_intake()`), если решение — принятие. При отказе и
  переадресации форма остаётся на «Обращении».
* В форме появился сигнал `send_in_chat`: заявки узлов `2.N`, `3` и калибровка
  порядка идут в текущий диалог. `restart_requested` (перезагрузка) остался
  только у этапа 1 — в `_send_node()` ветка `if str(kind) == "1"`.
* `main._on_send_in_chat()` ставит запись отложенной отправки и вызывает
  `_resume_pending_send()` **без** `_restart_browser_for_fresh_chat`: страница,
  профиль и переписка остаются, заявка и «Обращение.txt» прикрепляются обычным
  путём (тот же `pending_send`).
* Кнопка «Закрыть обращение» внизу «Цепочки этапов». Требует ответа ИИ по
  этапу 3, спрашивает подтверждение, вызывает `GovCase.close_work()`:
  `status = closed`, `closed_at`, `close_reason`, узел 3 отмечается
  выполненным. В списке обращений строка становится
  «Завершено · отработано 25.11.2026 21:00». Затем `main._on_gov_case_closed()`
  перезагружает браузер с чистым чатом.
* Попутно найдено и исправлено: `ogp_stages` брал шаги из `case.work_plan` —
  копии, которая отстаёт от активного варианта цепочки. Добавлен
  `GovCase.current_plan()` и хелпер `ogp_stages._plan(case)`: план всегда
  берётся у активного варианта, поэтому подпись кнопки и номер подэтапа не
  «прыгают» после переключения цепочки или пересборки порядка.
* Цепочки этапа 2 теперь разбираются и без `===`-маркеров, и без нумерации
  шагов (в выгрузке ИИ прислал «ЦЕПОЧКИ ЭТАПА 2» и «Об истребовании
  информации — …» обычными строками, и клиент не видел ни одной цепочки).

## Дополнено после аудита выгрузок

1. **Дата постановления раньше даты обращения.** В `Постановление.7z` документ
   этапа 1 был датирован 16.11.2026, а обращение — 25.11.2026: ИИ подставил дату
   из примеров промта. Добавлена проверка `check_gov_dates` (входит в
   `check_gov_document`): решается раньше обращения — замечание в «Замечаниях»,
   пустая дата замечанием не считается.
2. **Промт 1.34** (`Для новой версии/Текущий промт/promt 1.34.txt`):
   убрано «пять состояний» → «три состояния»; из правила 10 убрано состояние
   «Прекращено» (в клиенте его нет, ломало разбор); добавлено явное правило
   «даты берутся только из обращения».

## Решения пользователя (после вопросов по коллизиям)

1. **«Закрыть обращение» доступна всегда.** Если шаги цепочки не вынесены
   (или этап 1 не принят), кнопка не блокируется, а спрашивает: «Не всё по
   обращению №N отработано: шаги 2.2, 2.3 не вынесены. Закрыть всё равно?».
   Текст собирает `ogp_stages.close_reason(case)`.
2. **Чат не чистится после «Сформировать» и после PNG** (этапы 2 и 3).
   Мягкая перезагрузка страницы осталась только там, где ей место:
   * перед отправкой «Этап 1» — `_on_pending_send_restart`;
   * по кнопке «Закрыть обращение» — `_on_gov_case_closed`;
   * аварийно, если загрузка файлов не удалась после повторов
     (`_reload_for_upload_retry`, защита от «залипшего» чата).
   Ответ этапа 1 тоже остаётся в чате: сразу за ним ИИ присылает цепочки
   этапа 2, и перезагрузка рвала их приём.
3. **Этап 3 при отрицательном итоге по шагу.** Если ИИ по шагу 2.N ответил
   отрицательно (нарушение не подтверждено), перед «Этап 3» показывается
   предупреждение (текст — `ogp_stages.negative_steps(case)`).
4. **Архив версии.** В папке лежит `TestLegalUniversal_v63_полная_версия.tar.gz`
   — вся версия одним файлом (код, тесты, data, примеры, документация).
5. **Порядок в директории.** Из индекса Git убраны `.venv-test/`, `logs/`,
   `postanovleniya/`, папка лога `20261108-…`, `Замечания/`,
   `Постановление_3/4/Результат_1`, четыре SERP-дампа и скриншот; всё это
   перечислено в `.gitignore`. Дубли-копии PNG, лежавшие и в корне выгрузки,
   и внутри папки дела, удалены физически (10 файлов).
