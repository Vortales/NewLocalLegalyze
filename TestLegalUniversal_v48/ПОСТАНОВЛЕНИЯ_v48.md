## v45 — «Сформировать»: PNG постановления не создавался

Замечание пользователя: «"Проверка ИИ" всё ушло и отлично прошло, обращение
висит как "Отказано", но при нажатии кнопки "Сформировать", чтобы сделать
Постановление об отказе, он не создаёт .png файл». Ответ ИИ в чате при этом
был (постановление AG-2 об отказе в принятии обращения).

Разбор ответа ИИ показал: сам ответ разбирается правильно, PNG из него
строится. Значит, ответ до разбора не доходил — и причин оказалось три.

### Причина 1. После «Сформировать» ответ вообще никто не читал

Опрос чата включался в одном месте — после отправки заявки, но только для
«Проверки ИИ»:

```python
if ok:
    self._pending_send_finish(psend.STATE_SENT, record)
    if kind == "intake":          # ← только «Проверка ИИ»
        self._watch_document_answer()
```

Заявка на постановление уходит с `kind="document"`, поэтому после неё опрос не
запускался: ИИ отвечал в чат, а клиент чат не читал. PNG не печатался — и
никакого сообщения об ошибке тоже не было.

**Исправлено:** опрос включается после ЛЮБОЙ успешной отправки заявки
(`_watch_document_answer()` без условия). Тот же вызов добавлен в
`_auto_send_document_request`: авто-отправка может сработать позже, когда
окно формы уже закрыто.

### Причина 2. Дело искалось не то

Номер дела заполнялся только для «Проверки ИИ»:

```python
if str(record.get("kind") or "") == "intake":
    self._gov_intake_case = str(record.get("case_number") or "")
```

Документ по «Сформировать» сохранялся в НОВОЕ дело (`store.next_number()`):
PNG уходил в чужую папку, а в списке обращений появлялся дубль.

**Исправлено:** `_doc_case_number` берётся из записи для любого вида заявки,
и разбор документа ищет дело по нему (а не по «последней проверке»).

### Причина 3. В отказе печаталась фраза о вменяемом нарушении

В «УСТАНОВИЛ» документа об отказе появлялось «Указанные обстоятельства
образуют нарушение: пункта 14 части 1 статьи 16 Регламента …». Это норма
ОТКАЗА, а не состав: пункт 14 части 1 статьи 16 как раз говорит, что в
принятии отказывают.

**Исправлено:** в решениях без вменяемого нарушения (отказ в принятии, отказ
в удовлетворении, прекращение производства, завершение проверки) «Пункт
нарушения» и «Нарушенный акт» в этот вывод не попадают вовсе. Для этапа
санкции фраза остаётся.

Попутно: если ИИ не прислал вид решения, а в резолюции «в принятии …
отказать», предлагается «Об отказе в принятии обращения к рассмотрению» —
раньше мог получиться заголовок о принятии при резолюции об отказе.

### Проверено на ответе из замечания

Ответ AG-2 разбирается полностью: номер, дата, прокурор и удостоверение,
заявитель и ID, нарушитель и удостоверение, отдел, дата события, нарушенный
акт, пункт, нормативное основание, «УСТАНОВИЛ» и три пункта «ПОСТАНОВИЛ».

## v45.1 — «Сформировать»: ответ есть, но считается нашей заявкой

Лог `20261109-161442-5868-df44a7`, файл «Скопированный ответ ИИ по
Сформировать ответ.txt». В чате документ есть, PNG не печатается.

В журнале каждые 2,5 секунды:

```
documents.skip_own_request chars=35790
```

То есть клиент ЧИТАЛ ответ, но считал его нашей собственной заявкой.
Причина — примета «заявка на постановление» в списке «фраз, которые бывают
только в заявке». Но ответ ИИ начинается с ЦИТАТЫ заявки (в чате он виден
вместе с вложением «Заявка (отправлено в чат).txt»), и примета срабатывала на
настоящем документе.

### Что ещё нашлось при проверке этого ответа

| Проблема | Как проявлялась |
|---|---|
| примета «заявка на постановление» решала сама | настоящий ответ отбрасывался целиком (`skip_own_request`) |
| блок документа начинался с цитаты заявки | в «ПОСТАНОВИЛ» попадали пункты обращения («Данные о заявителе…», «Ксерокопия…») |
| ИИ написал «УСТАВНОРИЛ» | весь раздел «УСТАНОВИЛ» пропадал из документа |
| «Постановление вынес: Jonathan Raine» принималось за маркер | проверка писала «не указано, кто вынес постановление» |
| перенос строки внутри пункта | один пункт резолюции становился двумя |
| строка «Основание: …» в конце | попадала в резолюцию как ещё один пункт |
| подпись прокурора | приклеивалась к последнему пункту |

### Как исправлено

`is_own_request` переписан: порядок проверок — от надёжных признаков к слабым:

1. текст совпадает с заявкой → заявка;
2. в тексте есть сам документ («УСТАНОВИЛ» / «ПОСТАНОВИЛ» / «КОНЕЦ
   ПОСТАНОВЛЕНИЯ») → это ОТВЕТ, даже если он цитирует заявку;
3. заявка внутри текста → решает остаток (документ есть → ответ);
4. текст начинается заголовком «ЗАЯВКА НА ПОСТАНОВЛЕНИЕ ПРОКУРОРА» и строкой
   «Данные для подготовки документа» → заявка;
5. блок проверки обращения → ответ;
6. служебные пометки заявки → заявка.

Дополнительно:

* `extract_document_block` при цитате заявки начинает блок с заголовка
  «ПОСТАНОВЛЕНИЕ» + «Ведомство:» (`_document_body_start`), поэтому пункты
  обращения в резолюцию не попадают;
* `_normalize_heading` понимает опечатки заголовков («УСТАВНОРИЛ»,
  «ПОСТОНОВИЛ») — раздел фактов больше не теряется;
* строка «Постановление вынес: …» распознаётся как ПОЛЕ, а не как маркер
  документа — автор, должность и удостоверение снова в документе;
* перенесённые строки пункта склеиваются, подпись и «Основание:» в резолюцию
  не попадают.

принятии обращения к рассмотрению», номер AG-2, заявитель Palmer Blue

## v46 — постановление собирается только из документа, без лишних реквизитов

Замечание пользователя: «Текст распознаёт, но с ошибками. Сделай, чтобы текст
распознавался корректно и постановление вставлялись только те данные, что там
должны быть, а не иначе. Исправления сделай в новой версии… сделай корректную

проверил и ответ был корректно получен, обнови браузер. А то он завис на

Разбиралась выгрузка `Постановление_46v` (ответ `AG-1/ИИ-ответ.txt`) и логи
`20261109-163354-17316-d1a792`, `20261109-163609-17752-c3107a`.

### Что было напечатано в PNG (файл `AG-1/AG-1 — эт.1 принятие — стр.1…3.png`)

| Место в бланке | Что попало | Почему |

| «УСТАНОВИЛ» | абзац ИИ + весь наш промт («Обращение уже рассмотрено…», «ОСНОВАНИЕ ОТКАЗА…», «ЭТАП 1 — ПЕРВИЧНОЕ РЕШЕНИЕ…») и цитата заявки | блок документа не был найден — см. п. 1 |

| подпись | `J. Raine` вместо `Jonathan Raine` | строка подписи ИИ попадала в «автора» |

### 1. Причина всех ошибок разбора: блок документа не находился

```python
best = 0
for match in _DOC_HEADING_RE.finditer(raw):
    tail = raw[match.start():match.start() + 400].lower()
    if "ведомство:" in tail or "подразделение:" in tail:   # ← только так
        best = match.start()
```

Это окно искало после заголовка «ПОСТАНОВЛЕНИЕ» поле «Ведомство:». В этой
выгрузке порядок реквизитов другой — сразу «Номер:», «Дата:», «Вид документа:»,
поэтому `best` оставался нулевым, `extract_document_block` возвращал окно в
7000 символов ОТ НАЧАЛА ответа, а в нём лежат промт и цитата заявки. Отсюда и
«УСТАНОВИЛ» с инструкциями, и «ПОСТАНОВИЛ» с пунктами обращения.

**Исправлено:** заголовок документа ищется по любому из реквизитов
(`_DOC_HEADING_FIELDS`: «Ведомство:», «Подразделение:», «Номер:», «Дата:»,
«Вид документа:», «Вид решения:», «Заявитель:»). Блок теперь начинается ровно
с «ПОСТАНОВЛЕНИЕ»:

```
ПОСТАНОВЛЕНИЕ
Номер: AG-1
Дата: 09.11.2026
Вид документа: Об отказе в принятии обращения к рассмотрению
```

Дополнительно `is_chat_instruction` (он же `scrub_chat_text`) знает маркеры
нашего промта, которые ИИ копирует в ответ дословно: «Обращение уже
рассмотрено», «Оформи это решение постановлением», «ОСНОВАНИЕ ОТКАЗА (по
проверке обращения)», «ОТВЕТ ИИ ПО ПРОВЕРКЕ ОБРАЩЕНИЯ», «ЗАЯВКА НА
ПОСТАНОВЛЕНИЕ ПРОКУРОРА», «Данные для подготовки документа», «ЭТАП 1 —
ПЕРВИЧНОЕ РЕШЕНИЕ», «ОБРАЩЕНИЕ ГРАЖДАНИНА (текст целиком», «Оценивай ТОЛЬКО
само обращение», «Санкцию не назначай», «Определит ИИ по обстоятельствам».
Если ответ всё же придёт без заголовка, эти строки в документ не попадут.

### 2. Пункты формы обращения в резолюции

Даже при верном блоке ИИ иногда копирует в «ПОСТАНОВИЛ» пункты заявления.
Добавлен `is_appeal_form_point`: «Данные о заявителе», «Сведения о
нарушителе», «Предмет обращения», «Дата и время события», «Подробное описание
ситуации», «Ксерокопия…», «Электронную почту…», «Доказательства
правонарушения», «Дата подачи заявления», «Подпись и расшифровка» — это
реквизиты заявления, а не решения прокурора. `strip_signature_points`
выбрасывает такие пункты и пишет в лог `gov.appeal_form_point_dropped`.

### 3. Решения без номеров склеивались в один пункт

ИИ прислал резолюцию без нумерации:

```
ПОСТАНОВИЛ:
Отказать в принятии обращения …
Прекратить прокурорское производство …
Разъяснить заявителю, что …
Настоящее постановление вступает в законную силу …
```

Раньше все строки после «ПОСТАНОВИЛ:» склеивались в один пункт. Теперь
`_looks_like_point` считает каждую строку, которая начинается с решения
(«отказать», «прекратить», «разъяснить», «настоящее постановление», «копию»,
«обращение» …), самостоятельным пунктом — в PNG их четыре.

### 4. «Основание» печаталось с повтором одной статьи

`basis_text()` собирал «Пункт нарушения» и «Нормативное основание» как есть:
«пункт 14 части 1 статьи 16; …; часть 1 статьи 16 Регламента …». Добавлен
`_dedupe_basis_segments`: если ссылка без пункта говорит о той же статье, что
и ссылка с пунктом, она убирается. Итог:

```
Основание: пункт 14 части 1 статьи 16; Регламента подачи обращений в Офис
Генерального прокурора штата Сан-Андреас; статьи 27–28 Регламента подачи
обращений в Офис Генерального прокурора штата Сан-Андреас
```

### 5. Лишние реквизиты

* `is_place_placeholder` теперь отбрасывает «в месте проведения процессуальных
  действий», «в месте совершения», «на месте события» — это описание
  процедуры, а не адрес;
* `drop_placeholders` проверяет `event_place` отдельно (через
  `is_place_placeholder`) и пишет `gov.place_dropped`;
* если нарушитель не установлен, «Отдел сотрудника»/«Звание»/«ID» не печатаются
  вовсе;
* пустые поля по-прежнему удаляются как заглушки, поэтому «Отдел сотрудника:» и
  «Взыскание:» в бланке не появляются (`ИИ-документ.txt` содержит только
  заполненные реквизиты).

### 6. «J. Raine» вместо «Jonathan Raine»

В ответе есть и поле «Постановление вынес: Jonathan Raine», и строка подписи
«J. Raine». Строка подписи больше не может стать автором: имя берётся из поля,
а инициал в бланке остаётся только в росчерке подписи.

### 7. «Обстоятельства» и «УСТАНОВИЛ» — один и тот же пересказ

ИИ заполнил оба поля почти одинаково (пересечение слов 38 %), и в бланке шли
два абзаца об одном и том же. `_facts_restart_story()` (сравнение по значимым
словам, порог 0.34) убирает дубль: печатается «УСТАНОВИЛ», а не его пересказ.

### 8. «Проверка ИИ»: окно больше не висит на старом состоянии

Лог `20261109-163354-17316-d1a792`:

```
13:34:12  pending_send.sent kind="intake"
13:34:14  gov.intake.unparsed chars=12335     ← ответ ещё печатался
13:34:17  gov.intake.unparsed chars=12335
13:34:19  gov.intake.result case="1" state="Отказано" status="refused"
```

Ответ разобран и записан в дело (`cases/1/case.json` — «Отказано»), но окно
программы и список обращений остались на состоянии до ответа: пользователь
видел «Обращение №1: Отказано (…)» и решал, что всё зависло.

**Исправлено:** сразу после `gov.intake.result` вызывается
`_refresh_after_intake(case)`:

* `GovCasesDialog.reload()` — перечитывает дела с диска и перерисовывает
  список (выбранная строка сохраняется);
* перерисовка окна программы (`update()` у окна, статуса и плейсхолдера);
* через 0.9 с — `_reload_chat_after_intake()`: окно ИИ обновляется тем же
  путём, что и штатное восстановление страницы (`_recover_web`) — чат
  открывается заново, старое сообщение больше не «висит».

Обновление не запускается, если в очереди уже стоит заявка на постановление
(`pending_send`) — иначе она бы ушла в перезапущенный браузер дважды, и на
каждую проверку приходится ровно одно обновление (`_gov_intake_reloaded`).

## v47 — «Новое обращение» нужно нажимать один раз

Замечание пользователя: «В кнопке "Документ", внутри "Постановление Прокурора"
наш объект → кнопка "Новое обращение". Для создания в "Обращения" обращения
нужно 2 раза нажать на "Новое обращение"».

### Причина

Стартовый список обращений (`GovCasesDialog`) возвращал `None` в двух разных
случаях:

```python
if dialog.new_requested:
    return None            # пользователь нажал «Новое обращение»
return dialog.selected_case   # при закрытии окна тоже None
```

Форма `PostanovlenieProkuroraDialog` получала `case=None` и по одному этому
признаку решала, что дело не выбрано:

```python
self.ask_case_on_show = bool(ask_case) and case is None
...
def showEvent(self, event):
    if self.ask_case_on_show:      # ← открывается список обращений
        self.ask_case_on_show = False
        self._open_case_dialog()
```

Получалось: «Новое обращение» → форма → снова список обращений («Открыть
обращение») → и только второе «Новое обращение» создавало чистое дело.

### Исправлено

`main._choose_gov_case` теперь различает два случая и запоминает выбор:

```python
if dialog.new_requested:
    self._gov_case_new_requested = True
    return None
```

а форма открывается с `ask_case=not self._gov_case_new_requested` — раз
пользователь уже нажал «Новое обращение», второй раз список не показывается.
Признак сбрасывается при КАЖДОМ открытии «Постановления Прокурора», поэтому
прошлый выбор не влияет на следующее открытие, а старый вызов формы без
параметра (`ask_case=True`) работает как раньше: если дело не выбрано, список
открывается.

## v48 — после «Проверки ИИ» в чате лишнее вложение «Проверка обращения (заявка).txt»

Замечание пользователя: «после исполнения функции "Проверка ИИ" и после
получения ответа и после перезагрузки у меня помимо .pdf файла и Шаблон.txt
ещё привязан файл Проверка обращения (заявка).txt».

### Причина

Перед отправкой заявка ставилась третьим вложением:

```python
self.document_path = path          # _load_pending_document()
...
self._doc_request_text = path.read_text(encoding="utf-8")
```

После успешной отправки очищался только текст заявки (`_doc_request_text`
нужен, чтобы отличить свой запрос от ответа ИИ), а `document_path` оставался
выставленным. Поток вложений живёт по этому полю:

```python
def _required_count(self) -> int:
    return REQUIRED_CHAT_FILES + (1 if self.document_path else 0)

def _missing_files(self, names):
    ...
    if self.document_path and not _chat_has_file(names, Path(self.document_path).name):
        missing.append(self.document_path)      # ← заявка вкладывается снова
```

В v46 после корректного ответа окно ИИ обновляется (`_recover_web`), и новый
поток вложений снова видел `document_path` — в чате оказывались три файла:
`Memphis.pdf`, `Шаблон.txt` и «Проверка обращения (заявка).txt».

### Исправлено

Добавлен `_drop_document_attachment(reason)`: обнуляет `document_path` и
`_doc_sent_path` в главном окне и в работающем потоке вложений. Он вызывается
сразу после того, как заявка РЕАЛЬНО ушла в чат:

* `_pending_send_finish(STATE_SENT)` — путь отложенной отправки
  («Проверка ИИ» и «Сформировать» после чистого чата), лог
  `documents.attachment_dropped`;
* `_auto_send_document_request()` — путь авто-отправки, когда все файлы уже
  на месте.

Текст заявки (`_doc_request_text`) не очищается: по нему клиент отличает свою
заявку от ответа ИИ (`is_own_request`). Ветка «заявка не отправлена»
(`STATE_EXPIRED`) вложения не трогает — там заявка ещё нужна.

Итог: и после ответа ИИ, и после обновления окна в чате остаются только
`Memphis.pdf` и `Шаблон.txt`; заявка прикладывается заново только когда
пользователь снова нажмёт «Проверка ИИ» или «Сформировать».

### Тесты

`tests/test_v48_intake_attachment.py` — 6 тестов: очистка пути и потока,
вызов только в ветке успешной отправки, вызов в авто-отправке до ожидания
ответа, сохранение текста заявки, требование ровно двух файлов после очистки.
